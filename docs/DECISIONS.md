# 設計決策紀錄

> 每做一個重要決定就記一筆：決定了什麼、為什麼、考慮過哪些其他選項。

| 日期 | 決定 | 原因 | 其他選項 |
|---|---|---|---|
| 2026-09-29 | **收集全台北市 1300 站，但第一個模型只做大安區** | API 一次就回傳全部站點，只存一區跟存全部的抓取動作完全一樣，存全部的邊際成本接近零。反之若只存一區，日後想擴大範圍就要重新累積好幾個月 —— 反悔成本無限大。建模只做一區是為了讓第一個模型單純。 | 只收一區（PREP.md 原案）；全收且全建模 |
| 2026-09-29 | **兩段式儲存：每 5 分鐘寫小 Parquet → 每日壓縮成一個日檔** | 288 個小檔約 8 MB/天（240 MB/月）；壓成一個日檔後欄位壓縮效果好很多，只剩約 1–3 MB/天（30–90 MB/月）。用「只新增、不修改」的小檔而不是每 5 分鐘讀出大檔追加再寫回，是因為讀-改-寫中途失敗會弄壞整天的資料，而小檔失敗最多只損失那 5 分鐘。 | 直接 commit 不壓縮（三個月後數百 MB、上萬 commit）；GitHub Release 當主倉（每 5 分鐘上傳不現實）；Hugging Face Dataset（多一組帳號 token 要管，留待資料有價值後再發布）；Actions artifacts（只留 90 天，合併很痛苦） |
| 2026-09-29 | **資料放 repo 的 `data` 分支，每月備份一份到 GitHub Release** | 資料 commit 跟程式 commit 分開，主分支歷史保持乾淨好看（作品集考量）。Release 當離線備份，萬一 repo 出事不會全丟。 | 全部放主分支；獨立 data repo |
| 2026-09-29 | **repo 設 public** | 私有 repo 每月只有 2000 分鐘 Actions 額度，但一天 288 次 × 約 1 分鐘 ≈ 8600 分鐘/月，會直接爆掉。公開 repo 的 Actions 免費無限。反正是作品集本來就要公開。 | 私有 repo（額度不夠） |
| 2026-09-29 | **預測目標的定義延後到 phase 2 再定** | 原始資料存的是車輛數，標籤隨時能重算，現在急著決定沒有任何好處，而且等看到真實分布再定更準。目前傾向定義成「可借車輛 <= 1」而非 = 0，因為 = 0 太罕見（正樣本可能只有 2–5%），而且「剩 1 台」對使用者的體感跟「剩 0 台」一樣（走到站點時那台已經被騎走）。 | 現在就定 = 0；改成迴歸預測車輛數 |
| 2026-09-29 | **不看 accuracy，改看 PR-AUC 或固定精確率下的召回率** | 這是高度不平衡的分類問題，全部猜「借得到」就有 95% 準確率，accuracy 完全沒有鑑別力。 | accuracy、ROC-AUC（不平衡時也會過度樂觀） |
| 2026-09-29 | **不做本機備援收集器，改做斷線監控** | 擁有者下班後家裡沒網路，本機收集只能涵蓋上班時段（約 9–18 點），但這個專案最關鍵的時段是傍晚 17–20 點通勤尖峰 —— 恰好是斷網時間。備援填補的是 Actions 本來就跑得順的時段，投入產出比很差。改成每日檢查昨天收到幾筆，低於門檻就自動開 GitHub Issue（會寄 email），解決「靜默失敗」這個最會殺死專案的問題。 | Windows 工作排程器跑本機備援；不做任何監控 |
| 2026-09-29 | **天氣資料從第一天就一起收** | 天氣特徵 phase 3 才會用，但事後要把觀測歷史對齊到每 5 分鐘的時間點很麻煩，順手存下來最省事。 | phase 3 再開始收（要回頭補對齊） |
| 2026-09-29 | **工作方式改為「一次只做一步」** | 原本是「一次只做一個 phase」，但一個 phase（例如 phase 0 有 6 個步驟）太大，中途走偏了要改很貴。改成一步一確認。 | 一次一個 phase |
| 2026-09-29 | **以「換電腦轉移方便」為設計前提，repo 是唯一真相來源** | 擁有者之後會把專案搬到另一台電腦長期保存。因此目標定為：只要 GitHub 上的 repo 還在，本機電腦壞掉、重灌、換新都不會丟任何東西。唯一不在 repo 裡的是 `.env`（金鑰不能 commit），這點寫進 `SETUP.md` 明講。 | 用雲端同步資料夾備份（會弄壞 git、產生衝突複本） |
| 2026-09-29 | **資料放在同一個 repo 的 `data` 孤兒分支，不另開 repo** | 轉移時「一次 `git clone` 拿到全部」是最重要的。同 repo 的分支在 clone 時物件會一起下載，不用記第二個網址、不用管兩個 repo 的權限。用孤兒分支（跟 main 沒有共同歷史）則讓資料的 commit 紀錄跟程式完全分開，main 的歷史保持乾淨。 | 另開 data repo（要記兩個網址）；一般分支（會帶著程式碼、歷史混在一起）；只用 GitHub Release（沒辦法每 5 分鐘上傳） |
| 2026-09-29 | **程式裡所有路徑從 `__file__` 推算專案根目錄，不用執行時的工作目錄** | 用相對路徑 `data/raw` 的話，只有在專案根目錄執行才正確；從別的地方執行會把資料默默存到錯的位置而且不報錯。改成從程式檔位置推算後，換電腦時不管專案放哪個磁碟、路徑有沒有中文或空格都不用改程式。 | 相對路徑（換位置就壞）；寫死絕對路徑（換電腦一定壞） |
| 2026-09-29 | **pandas 鎖 `>=2.2,<3`** | pandas 3.0.6 的 `groupby.pyd` 會被 Windows 11 智慧型應用程式控制封鎖（太新、沒有信譽紀錄），import 直接失敗。2.2.3 正常。 | 不鎖版本（換電腦重裝時會再踩一次） |
| 2026-09-29 | **requirements 拆成 `requirements-collect.txt`（Actions 用）和 `requirements.txt`（開發用）** | Actions 每天要裝 288 次套件，但收集程式只需要 requests + pyarrow，pandas 又大又慢且用不到。拆開可以明顯縮短每次執行的時間。 | 單一 requirements（每次都裝 pandas） |
| 2026-09-30 | **cron 用 `*/5` 單次執行，不做「一次 job 內連續取樣 3 次」的批次法** | 批次法（每 15 分鐘跑一次、job 內 sleep 取 3 個樣）能保證樣本間隔精準，但一次被跳過就損失 15 分鐘而不是 5 分鐘，而且複雜很多。先用最單純的做法，等 phase 0-6 的覆蓋率報告拿到真實數字再決定要不要換 —— 現在換是憑猜測，那時換是憑資料。 | 每 15 分鐘批次取樣 3 次；改用外部主機跑 cron（穩定但要付錢/多學設定） |
| 2026-09-30 | **`data` 分支用 git 底層指令（`hash-object`/`mktree`/`commit-tree`）建立，不用 `git checkout --orphan`** | `checkout --orphan` 會把 main 的所有檔案留在工作目錄並標成已暫存，接著必須 `git rm -rf .` 才能清乾淨 —— 一個手滑就刪掉工作目錄的檔案。底層指令直接組出一個 root commit，完全不碰工作目錄和索引，零風險。 | `checkout --orphan` + `git rm -rf .`（有刪錯檔的風險） |
| 2026-09-30 | **workflow 用兩次 `actions/checkout`：main 放程式、data 放到 `data-branch/`** | 程式在 main、資料在 data，兩個分支沒有共同歷史，一次 checkout 只能拿一個。取兩次各放不同資料夾最直觀。data 分支用 `fetch-depth: 1`，因為它每天會多 288 個 commit，抓完整歷史三個月後光下載就要好幾分鐘。 | 在同一個 checkout 裡切換分支（會把工作目錄搞亂）；用 `git worktree`（Actions 上沒有比較簡單） |
| 2026-09-30 | **push 失敗時 `fetch` + `rebase` 重試 5 次，另加 `concurrency` 序列化** | cron 延遲會讓兩次執行重疊，兩個 job 同時 push 必有一個被拒。`concurrency` 讓它們排隊（擋掉絕大多數情況），rebase 重試當第二層保險。因為每次新增的檔名都不同（檔名是來源時間），rebase 不會衝突。 | 只靠 concurrency（仍有極少數競爭）；push 失敗就放棄（會靜默漏資料） |
| 2026-09-30 | **⚠️ 未解決：`data` 分支的 git 歷史會一直長大，交給 phase 0-5 處理** | 每個小檔 11.2 KB × 288 次/天 ≈ 3.2 MB/天 ≈ 97 MB/月。phase 0-5 的每日壓縮只縮小「工作目錄」，git 歷史裡的舊物件永遠留著，所以 repo 半年後約 580 MB。預定解法：每月備份到 GitHub Release 之後，把 data 分支重建成新的孤兒分支（只留壓縮後的日檔）並 force push —— 反正 Release 已經是離線備份。 | 不處理（repo 無限膨脹）；不每次 push（資料只在 runner 上，失敗就全丟） |
| 2026-09-30 | **壓縮流程是「先核對才刪檔」的四步式，不是邊合併邊刪** | 壓縮的本質是刪掉原始資料，而 YouBike 沒有歷史資料 API —— 刪錯就永遠回不來。所以流程是：合併 -> 寫日檔 -> **把日檔重新讀回來**核對筆數/欄位/時間點數量 -> 全部對得上才刪小檔。刻意不信任「剛剛寫檔應該沒問題」。實測用一個壞檔混進去，程式會中止且小檔一個都沒刪。 | 邊讀邊刪（省記憶體但刪錯無法復原）；只比對筆數不重讀（漏掉寫檔損壞的情況） |
| 2026-09-30 | **日檔按「站點 -> 時間」排序，不是按時間排序** | 之後做特徵工程幾乎都在看「同一個站的時間序列」（例如「30 分鐘前有幾台車」），同站資料排在一起讀起來快很多。附帶好處是同站連續時間點的車輛數很接近，Parquet 壓縮這種連續相似值特別有效。實測 288 檔 3.2 MB -> 456 KB（小 7.1 倍），耗時 7 秒。 | 按時間排序（合併時的自然順序，但查單一站要掃全表）；不排序（壓縮率差） |
| 2026-09-30 | **壓縮程式每次掃「所有」待壓縮的日子，不是只壓昨天** | 排程可能連續失敗好幾天，等你發現時已經積了一堆。每次都掃全部就不需要人工補做，而且這也讓程式天然是可重複執行的（idempotent）—— 重跑不會壞掉。 | 只壓昨天（失敗後要人工補） |
| 2026-09-30 | **推送邏輯抽成共用的 `scripts/push_data.sh`，兩個 workflow 共用** | collect（每 5 分鐘）和 compact（每天）要做完全一樣的 commit + push + 重試。在兩個 YAML 各寫一份的話，改了一邊忘了另一邊就會出現「一個有重試、一個沒有」這種很難察覺的不一致。 | 兩個 YAML 各寫一份（會走鐘） |
| 2026-09-30 | **commit 訊息用 `git diff --no-renames` 產生** | git 預設會做改名偵測：日檔內容跟被刪的小檔高度相似，會被判定成「改名」而不是「新增+刪除」，`--diff-filter=A` 抓不到日檔，commit 訊息就變成沒意義的 `update (+0 -287)`。這是實際測出來的 bug，不是預想的。 | 用預設行為（訊息會錯） |
| 2026-09-30 | **compact 排在台北時間凌晨 3 點（UTC 19:00），且跟 collect 用不同的 concurrency 群組** | 要等前一天真的結束（過午夜）才能壓，又想避開整點 —— 整點是全世界 cron 最擠的時候，延遲最嚴重。用不同群組讓兩者可以同時跑，因為 compact 動「以前」的檔案、collect 動「今天」的，路徑不重疊，rebase 重試可以乾淨處理（已用假的 origin 實測驗證）。 | 午夜 00:05 就壓（時區邊界容易算錯）；跟 collect 同群組（compact 可能被排隊中的 collect 擠掉） |
